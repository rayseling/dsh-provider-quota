# Agent Note: 卡片只写给 rc.8 的 mirror，不同时迁就两个宿主

Status: implemented

`a39aac3` · 2026-08-20

## 问题

上一版让卡片学会了 rc.8 的「写入即答复」折叠，但把 rc.7 的重读路径留在旁边，
两条路并存。留下来的不只是一个分支，还有一整套只为等那条旧路径而存在的机制：
`settle()`——它存在的理由是 rc.7 的 `scope.load()` 是一次**异步排队的读**，
卡片必须保持 busy 直到它落地，否则下一次保存会撞上一个已被取代的 revision。

## 决定

只写给当前 harness（rc.8）。删掉第二条路径，连同 `settle()` 一起。

rc.8 没有那次读：mirror 不批处理地通知，scope 在那次通知里就派生完成，
所以 `acceptView` 返回时 revision 已经推进了。`save` 依次折叠、清空、释放，
「答复完成」和「已是最新」之间没有窗口留给第二次写入掉进去。

`ctx.settingsScope.describe()` 从此直接调用，不再探测。
没有它的 harness 会在 `mount` 里抛，而 `apply` 已经接住了——
和这里每个服务一样的「不把宿主砸死」姿态：最坏的结果是没有卡片。

## 考虑过的方案

- **继续同时支持 rc.7 和 rc.8。** 没选：两条路径里只有一条会被真正跑到，
  另一条随时间腐坏而无人察觉；而 `settle()` 这类只为旧路径存在的机制，
  会被后来的人当成通用机制去用。README 已经写明了卡片要求的 harness 版本，
  宿主那半边（真正提供模型路由的部分）没有这个下限。
- **探测 `describe()` 是否存在，缺了就降级。** 没选：降级到什么？
  没有 mirror 就没有卡片，探测只是把「抛在 mount 里」换成「静默地什么都不做」，
  而后者更难查。
- **保留 `settle()` 以防将来又需要等待。** 没选：没有当前的调用方，
  就没有人知道它该在什么条件下被调用；「以后可能用到」的机制永远不会被删。

## 后果

- 三条 fencing 测试重写了：原来的桩里有一个 harness 已经不再提供的 `load`，
  它们钉的是一个不存在的契约。现在两个共享 fake 都带 mirror、都没有 `load`，
  测的是：连续两次保存会在第一次的产物上 fence、折叠严格发生在卡片释放之前、
  以及一个会抛的 mirror 代价是一个 revision 而不是卡死一次保存。
- 顺带修正了头注释里一处不实：卡片自从长出菜单之后，就同时向模块表要
  react 和 UI primitives 两个模块，而注释里只写了 react。
