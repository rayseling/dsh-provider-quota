# `validate` 里不放依赖外部世界的检查

> **0.5.0 起本仓库不再有这段代码**：模型路由交回宿主的 `llm-pi-ai`，本文留档，再写同类代码时先读它。下面的符号名是当时的，本仓库已查不到。

2026-08-25

## 问题

`SettingsProvider.installSection`（当时叫 installSettingsSection）的 `validate` 钩子看起来是「写入前校验」的地方，
所以「`enabledModels` 里的模型必须在目录里」很自然会被写进去。

但这个钩子在 seam **解析**这份设置时也会跑，也就是每次启动一遍。
一旦它抛异常，整份 section 被拒绝——包括同一份设置里毫不相干的字段。
pi-ai 升级改名或下架一个模型，就够让用户设的上下文长度在下次启动时蒸发。
完整故事见 [`0001`](../postmortems/0001-settings-validate-runs-on-read.md)。

## 决定

按「这条检查依赖什么」分流，而不是按「它看起来是不是校验」：

| 检查依赖 | 放哪 | 例子 |
|---|---|---|
| 外部世界（目录、环境变量、文件） | **读取时过滤** | selectableModelIds() 丢掉目录里没有的 id |
| 只依赖值自身的形状 | `validate` | assertEnabledModelShape()：非空、不重复 |
| 组合配置里的值 | 加载时严格校验，大声报错 | 它随插件版本钉死，写错是部署方的 bug |

`modelOverrides` 留在严格那一侧：它点名的是用户**刻意**设过尺寸的模型，
目录里没有这个 id 是配置错误，不是漂移。

## 考虑过的方案

- **在 `validate` 里检查，但捕获异常只警告不拒绝。** 没选：`validate` 的返回值语义是
  「这份设置能不能存」，把它变成「存但记一行日志」会让真正该拒的写入也进去。
  而且异常已经被外层 `catch` 吞过一次了——那正是事故的形状。
- **区分「写入时」和「解析时」两个钩子。** 没选：这要改 harness 的 settings seam，
  而本插件是它的下游。真要提这个改动，也应该先在这里把规则写清楚。
- **干脆不校验 `enabledModels`。** 没选：空名单和重复项是**用户自己**能造出来的错误，
  当场拒绝比事后过滤对用户更好——而且这两条检查不依赖外部世界，放 `validate` 是安全的。
- **读取时过滤 + 同时在 `validate` 里也拒。** 没选：这就是事故本身。
  两处都做，等于外部世界的任何变化都能让整份设置蒸发。

## 后果

- 一个目录里已经没有的模型 id 是**漂移**，不是错误：读取时丢掉，不连累同一份设置里的别的字段。
- 代价是「用户写了一个拼错的模型 id」不会被当场拒绝，只会静默地不生效。
  这是刻意选的：拼错一个 id 的后果是少一个模型，而拒绝整份 section 的后果是丢掉全部设置。
- 卡片读的是**未过滤**的完整目录，所以组合配置即使只启用一个模型，
  用户仍然可以在卡片里把别的模型勾回来。
